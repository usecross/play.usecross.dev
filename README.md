# CrossInertia Playground

An in-browser playground for [CrossInertia](https://github.com/usecross/cross-inertia): Python runs in Pyodide, with a browser Service Worker routing preview requests to a FastAPI ASGI app. There is no backend Python server.

- **Site:** [play.usecross.dev](https://play.usecross.dev)
- **Repository:** [usecross/play.usecross.dev](https://github.com/usecross/play.usecross.dev)

## Current milestone: real CrossInertia

The default starter is a small **Tasks** app, laid out like a project from the official template. It uses the actual CrossInertia renderer for HTML, page JSON, partial reloads, deferred and optional props, validation errors, version conflicts, and manifest-generated JavaScript/CSS tags. The handwritten protocol helper and fake-library fallback have been removed.

> **Requires CrossInertia 0.22.2+.** Earlier releases start a thread while resolving props inside an async route, which fails in Pyodide. 0.22.2 ([cross-inertia #146](https://github.com/usecross/cross-inertia/pull/146)) resolves plain and sync props without one.

See [the milestone notes](./docs/real-cross-inertia.md) for evidence, constraints, and the next steps.

### Working

- Real FastAPI → CrossInertia → HTML/JSON responses inside Pyodide
- Inertia React client: pages under `frontend/pages/` in a persistent layout, `<Link>` visits, and `useForm` posts that redirect with 303
- Shared props (`inertia_share`), validation errors next to their field, and flash messages carried across a redirect by the session cookie
- Partial reloads (the task filter), `defer()` and `optional()` props (the Stats page)
- ASGI `root_path`: redirects and Inertia URLs stay under `/preview/`
- Real Jinja template and a Vite-shaped manifest, generated by esbuild, resolving hashed JavaScript/CSS in the VFS
- Visible initialization failures; no dependency stubs
- SQLite persisted in IndexedDB: tasks survive a full page reload and closing the tab
- One tab runs Python at a time; another tab waits and takes over with the saved data
- Editing every starter file: `app.py` and the modules it imports, such as `db.py`, the template, and the React frontend. Frontend edits are bundled in the browser with esbuild-wasm, and a new bundle changes the Inertia asset version
- Editing dependencies in `pyproject.toml`: **Restart Python** installs them in a new worker while the old one keeps serving, then switches with the data kept; a failed install leaves the old one running
- A **Network** panel under the preview lists every request the app answers, labelled by what it is in Inertia's protocol (document, Inertia visit, partial reload, redirect, version conflict, asset), with its headers, payload, response and page object: which props came back, which are shared, deferred or left out of a partial reload
- Errors thrown in the running preview, such as a render error or an import the import map doesn't provide, show under the editor
- Edits are saved in the browser and restored on reload; **Reset to starter** discards them and **Clear data** empties the database, each without touching the other

### Not implemented yet

- npm packages beyond the template's import map (React, React DOM and Inertia from pinned CDN URLs)
- Django/WSGI, SSR, WebSockets/SSE, or cross-origin runner isolation
- Async prop callbacks that need an event loop/thread bridge; this milestone uses plain props

## Quick start

### Prerequisites

- [Bun](https://bun.sh/) **1.4+** (the checked-in lockfile uses version 2)
- [uv](https://docs.astral.sh/uv/) on `PATH` for the native Python test
- Internet access to PyPI, jsDelivr, and esm.sh
- For Wrangler / deployment: **Node.js 22+** on `PATH`

```bash
bun install --frozen-lockfile
bun run dev
```

Open http://localhost:3000. The preview stays blank until the Service Worker controls the page and the real Python package and starter are initialized.

### Tests

```bash
bun run typecheck
bun run test:python       # Python 3.12; uv installs it if needed
bun run test:install      # First time: install Playwright Chromium and WebKit
bun run test             # Vite development server, in Chromium and WebKit
bun run test:production  # Built assets on Wrangler's local runtime
```

To use an installed Chrome locally instead of Playwright's bundled Chromium:

```bash
PLAYWRIGHT_CHANNEL=chrome bun run test
PLAYWRIGHT_CHANNEL=chrome bun run test:production
```

Tests verify:

- Real CrossInertia rendering with thread creation, Vite probes, and port scans forbidden
- Manifest-derived asset version and JS/CSS delivery through the Python VFS
- Adding, toggling, editing and deleting tasks, validation errors, flash messages, and preview reload
- Mount-prefix preservation, partial reloads, deferred and optional props, version conflicts, and invalid input
- A failed wheel download produces a visible error and never a fake successful preview

CI runs the native regression test and both browser configurations. Tests that intercept requests from a Web Worker (wheel and esbuild downloads) run only in Chromium, because Playwright's WebKit can't intercept them. Firefox isn't in CI yet: the playground works there, but Playwright's Firefox driver intermittently loses the preview iframe after it reloads.

## Project structure

```text
apps/shell/                      Vite shell, SW entry, preview host
  src/App.tsx                    React + shadcn/ui layout: file sidebar, editor, preview
  src/runtime.ts                 Starts Python, applies edits, exposes state to the UI
  src/editor.ts                  CodeMirror 6 editor, loaded lazily
packages/runner/
  sw.ts                          Browser fetch interception and virtual cookies
  python-worker.ts               Pyodide installation, VFS, serialized requests
  asgi-bridge.py                  HTTP → ASGI adapter
  browser_inertia.py              CrossInertia's browser settings: runtime mode and mount path, not a protocol implementation
  starter-files.ts                The starter's files and build, as the VFS and editor get them
packages/starters/
  index.ts                       Which starter runs, and reading its files from examples/
  runtime.json                   Pyodide version
packages/bundler/                esbuild bundle of the frontend, at deploy time and in the browser
examples/tasks/                  The default starter
  app.py                         FastAPI routes, shared props, validation
  db.py                          SQLite under PLAYGROUND_DATA_DIR
  pyproject.toml                 Starter's Python dependency pins, including CrossInertia
  templates/app.html             inertia_head() / inertia_body()
  frontend/app.tsx               createInertiaApp and the page map, bundled with esbuild
  frontend/components/Layout.tsx Nav, flash message, open-task count
  frontend/pages/                Tasks/Index, Tasks/Edit, Stats
examples/counter/                The first starter; it returns with the starter picker
scripts/                         Native Python test runner
```

The example files are the source of truth—there is no second copy embedded inside TypeScript. The frontend is bundled when the shell builds (a Vite plugin calls the same `bundleFrontend` the browser uses), so a first visit doesn't download esbuild-wasm; `bun run test:python` writes the same build to `static/build/`.

## Request flow

```text
Preview request: /preview/tasks
  → Service Worker
  → BroadcastChannel to shell
  → MessageChannel to Python worker
  → ASGI scope: path=/preview/tasks, root_path=/preview
  → FastAPI route /tasks
  → CrossInertia's real renderer / manifest / Jinja template
  → Response back through the bridge to the browser
```

The starter uses CrossInertia as documented: `InertiaDep` with its default settings, ordinary sync or async routes, and `app.frontend()` for the frontend build. Pyodide has no threads, so the ASGI bridge runs the work Starlette and FastAPI would put in a thread pool (sync routes and dependencies, file reads) inline. `browser_inertia.py` applies CrossInertia's browser-only settings before the starter loads: production mode without an HTTP probe, an explicit Vite port instead of a socket-based port scan, and the `/preview` mount (ASGI `root_path`) in asset URLs. Rendering is unchanged, and the starter's own code has no `/preview` in it. See [architecture](./docs/architecture.md) and [milestone details](./docs/real-cross-inertia.md).

## Deployment

Hosting uses Cloudflare **Workers Static Assets**, not Pages:

- Config: `wrangler.jsonc`
- Worker: `play-usecross-dev`
- Assets: `apps/shell/dist`
- Custom domain: `play.usecross.dev`
- Fallback: `play-usecross-dev.patrick-arminio.workers.dev`

Cloudflare's [Workers Builds](https://developers.cloudflare.com/workers/ci-cd/builds/) deploys the site from GitHub; there is no deploy workflow or API token in this repository. It is set up on the `play-usecross-dev` Worker under **Settings → Builds**:

- Repository: `usecross/play.usecross.dev`, root directory `/`, production branch `main`
- Build command: `bun run build` (Workers Builds installs dependencies from `bun.lock` first)
- Deploy command: `npx wrangler deploy`
- Other branches: builds on, with `npx wrangler versions upload`, so each branch gets a preview URL

Every push to `main` deploys. Workers Builds does not wait for the GitHub CI checks, so keep `main` green. Do not change DNS for `auth`, `docs`, or `inertia.usecross.dev`.

To check a deploy or a preview in a real browser, run the browser suite against it:

```bash
PLAYWRIGHT_BASE_URL=https://play.usecross.dev bun run test
```

`bun run deploy` still deploys by hand with your own `bunx wrangler login`. Avoid it while a Workers Builds deploy is running.
